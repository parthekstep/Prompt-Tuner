The shift

From: a human dials the bot, listens, writes up what broke, hand-edits two language files, hopes nothing else moved, and re-tests only the variant they remember.
To: a persona agent calls the bot, the transcript is graded against 93–114 checklist items, the fix is applied to the master language and mirrored, deployed, and re-tested — per variant.

What is real today

  • Agent-to-agent voice testing — used to green-light 8 bots and catch 7 shipping decisions on 2026-08-01.
  • Daily cloud regression + digest email — live, machine-off-proof, verified delivering, and it now audits its own fleet coverage after we caught it under-covering two live bots.
  • 67-pattern bug taxonomy — every fixed bug teaches the pre-flight auditor.
The ask.  (1) Adopt the 3-tier testing standard as the definition of "done" for any voice bot at EkStep.  (2) Approve Purple Dots as the second project on the rail.  (3) Unblock the weekly live-call tier — it needs platform keys placed in CI secrets, not engineering.

02 The problem

A voice bot does not stay correct. It drifts — silently, in every language at once.

03 Cost of the status quo

Manual testing is not just slow — it is what blocks campaigns from going live

Every cost below is a consequence of one root fact: verification was a human activity, and humans do not scale across languages, directions, and 1,500-line files.

1 · Discovery is late and lumpy

Issues surface in a batch at scale-test time, not at edit time. Then you need back-to-back changes under deadline — the highest-risk way to touch a live prompt.

Evidence: 25 logged prompt changes landed on a single day (2026-07-20); 12 on 07-13; 11 each on 07-27 and 07-29.

2 · Every new feature pays the re-verify tax

Shipping anything new means re-verifying everything old. With no automated regression, that cost is paid in human hours or skipped — and skipping is how the next batch of bugs is born.

Evidence: a single 2026-08-01 campaign required 7 critical decisions, 16 mechanical sync fixes, and 17 graded live calls to clear 8 bots.

3 · Extrapolation ships bugs

"It works in Hindi, so Kannada is fine" is the cheapest shortcut and the most expensive mistake. Runtime adherence, ASR and TTS differ per language — a byte-identical edit lands differently.

Evidence: Maya-inbound doubled the phone prefix to +91+91… while Maya-outbound passed. Extrapolating would have shipped it.

4 · The bottleneck is the campaign, not the engineer

A bot that cannot be verified cannot be pointed at real callers. Manual verification therefore sits directly on the critical path to a campaign going live — the queue is not "engineering capacity", it is confidence. The 2026-08-01 campaign found a ship-blocker before launch: three inbound bots would have offered jobs that do not exist, because their examples still described an old inventory. That is the class of defect that reaches a real job-seeker.

5 · Institutional memory evaporates

Without a written taxonomy, the same bug class is re-discovered by whoever is unlucky next. A rollback on 2026-07-23 shows the trap: an attempt to force a tool call by reframing it as "silent" made the model stop calling the tool entirely. Nothing but a written pattern stops that from recurring.

Sources: the three CHANGELOG.md files (per-day entry counts, the 07-23 rollback)  ·  raya/signals-expansion/e2e/DECISIONS-AND-FIXES.md (CD1–CD7, M1–M17, the CD2 ship-blocker)  ·  raya/signals-expansion/e2e/LEGACY-REGRESSION.md (the Maya-inbound phone-doubling bug)  ·  CLAUDE.md ("recipe-for-disaster rule")

No fix without a transcript. A prompt is never edited off a bug report, a hunch, or a static finding alone. Pull the real call, read the tool-call payloads, confirm the bug.

The grading rule that makes it trustworthy

Read tool_calls[].function.arguments, not just what was spoken. That is where payload bugs live — a stripped-hyphen job_id, a numeric record number where a UUID belongs, an empty profile_id, a platform hold_message narrating a step the prompt says is silent. A grader that reads only content sees a clean call and misses the bug entirely.

Known limits, stated plainly

  • One tester = one persona at a time. Its prompt is the persona, and the callee receives no per-call arguments — so different scenarios run serially.
  • Inbound bots cannot be dialled by the tester. They are tested via an inbound-via-outbound workaround; anything unverifiable is marked VERIFY-PENDING, never "done".
  • Telephony bridging is intermittent and call creation is rate-limited (~1 per 13 s). Failed dials are retried, not counted as bugs.
  • Voice-bridge echo: the tester sometimes parrots the bot. Structural items still grade from tool payloads; persona-dependent probes do not.
  • Backend and runtime tool-adherence failures are not prose-fixable. They are escalated, not patched.

The honesty discipline this produces

5 changelog entries carry an explicit VERIFY-PENDING. One entry is an outright rollback. The log refuses to claim "done" on an untested change — which is exactly why the green results elsewhere in this deck are worth something.

09 The testing standard

Three tiers. A change is not done until all three pass, in order.

Each tier exists because skipping it burned us. This is the standard we are proposing EkStep adopt for any voice bot.

Tier 1

Fix verification

Did the bug actually get fixed?

Reproduce the exact reported failure and confirm it is gone — in a real call transcript, on each affected variant.

Why it exists: "looks fixed" is not fixed. No transcript, no claim.

Shipped via /voice-test
Tier 2

Blast-radius regression

Did the fix break its neighbours?

Enumerate what the change could touch — the same section, the shared agnostic logic, the mirrored twin, the tool payload — and test around those areas on each variant.

Why it exists: this is the tier that catches "fixed X, silently broke Y". On 2026-07-23 a fix to stop a narration made the model stop calling the tool. Reverted.

Shipped manual enumeration + /sync-check
Tier 3

Standing regression

Has anything drifted since we last looked?

A scheduled pass over the whole fleet, running in the cloud so it survives the developer's machine being off. Findings are mailed as a digest.

Why it exists: drift is nobody's ticket. Without a standing check it is found by a caller.

Shipped daily static   Planned weekly live-call
The law that sits across all three tiers: test every variant — never extrapolate. Hindi and Kannada. Outbound and inbound. Each bot separately. Even when the edited logic is byte-identical agnostic content, because runtime adherence, ASR and TTS differ per language. Static verification is necessary and never sufficient.

The detection heuristic is the valuable part — three examples

D31  Create-then-apply batched in one turn → empty profile_id

Cause: the prompt said "ONE clean sequence in a single turn", so both tool calls were emitted together — the apply's arguments were built before the create's result existed.

Detection: grep the apply sequence for "single turn" / "back to back" / "whole sequence" applied to a create→apply pair. That wording is itself the bug.

D34  The platform narrates a step the prompt says is silent

Cause: the voice platform injects a hold_message parameter into every tool call; the model writes a natural sentence into it and the platform speaks it.

Detection: the tell is that grepping the prompt finds nothing — you must read the tool-call arguments. A silence rule that never names hold_message is insufficient.

G1  A placeholder printed before its own label kills the branch

Cause: Consider ${new_seeker} as new_seeker interpolates to "Consider no as new_seeker" — the value is presented as the label, so nothing binds and the branch is dead.

Detection: mentally interpolate every binding phrase. If it reads "<value> as x" instead of "x = <value>", flag it. And the runtime test: if behaviour is invariant to the variable's value, the gate is dead.

11 Multi-language integrity   Shipped

A fix in one language that does not land in its twin is a regression

Every edit is classified before it is mirrored. This is the discipline that makes a bilingual bot maintainable at all.

Language-agnostic → copied verbatim

Call-flow logic, phase and step structure, input-variable names, tool rules and JSON payloads, conditions and routing, prohibited-behaviour rules, dignity checks, the section skeleton itself.

Language-specific → translated & adapted

Spoken greetings, example dialogues, TTS number-to-word spellings, script rules, tone markers, culturally-adapted prohibited phrases, local place names — Bengaluru and Mysuru, not Pune and Ghaziabad.

The rule that surprises everyone

Instructions are ALWAYS in English — every rule, heading and condition, in every language file. The only Hindi or Kannada in a prompt is what the agent literally speaks. That is precisely why a Hindi file and its Kannada twin can share identical instructions and differ only in quoted spoken text. A section whose rules are written in Hindi is itself a bug — and has been logged as one.

The bug that proved the law

2026-08-01. Six legacy bots were restructured and voice-tested. Maya-outbound passed. Extrapolating from it would have been the obvious, cheap call.

Testing Maya-inbound independently caught a real per-variant bug: phoneNumber:"+91+91…". The variable already carried +91, but the literal template +91${contact_phone} made the model double it → the profile lookup returned empty and the profile creation 400'd.

Fixed in all 6 rewrites and re-verified. The log's own conclusion: "this is the 'test every variant' rule paying off — extrapolating from Maya-out passing would have shipped the bug."

Deliberate divergence is now machine-checkable

Some differences between languages are approved decisions, not drift. A registry (raya/divergences.json) records them as narrow carve-outs, so /sync-check reports them as expected — and never "corrects" an owner's decision behind their back. Anything outside the carve-out is still audited normally.

13 The blind spot we found in ourselves   Shipped

The daily check was silently under-covering the fleet. Now it audits itself.

This is the most uncomfortable slide in the deck, and the one that should make you trust the rest of it more.

What was wrong

The suite discovered its bots from a hard-coded list of 16 filenames, while raya/agents.json carried 18 live conversation targets marked deploy:true. Two of them — DKB inbound Hindi and DKB inbound Kannada — were never checked by a single run.

Worse than the gap itself: the digest email reported "16 bots checked" and read as full coverage. Nothing in the output hinted that two live bots were missing. A green digest meant "the 16 I happen to know about are fine."

Found by an adversarial review of the suite — not by the suite.

Before
hard-coded 16 filenames
→ 2 live bots invisible
→
After
agents.json is the source of truth
→ 18 checked, gaps raise CRITICAL

What we changed

  • coverage_gap() self-check. Every run reads agents.json and emits a CRITICAL finding if any live deploy target is not being checked. The suite can no longer be quietly incomplete.
  • Proven with a negative test. We hid a bot from the discovery list and confirmed the critical actually fires — a check that has never failed is not a check.
  • build_fleet_manifest.py. Generates fleet.json from agents.json plus the suite's own derivation, with a CI-safe --check mode. Kills the hand-maintained list that caused this in the first place.
  • Both newly-covered bots came back clean — the gap was in our coverage, not in those bots.
The principle: a quality system that can silently under-cover the fleet is worse than no quality system, because it manufactures false confidence. So the first thing it now checks is whether it is checking everything.
The same review found two more places the rail was hard-coded to the original three bots   Both fixed

prompt-version.sh — snapshot & rollback

It matched only kkb|dkb|maya, so a fourth project could not be snapshotted or rolled back without editing the script. It now discovers bot folders — the safety net extends to a new project with zero code changes.

raya_call.py — the transcript reader

It printed only three KKB-era keys, so for any other bot the call inputs read as absent — quietly undermining the repo's own rule to root-cause against the input args before editing. It now prints the full agent_args and call_output.

17 Beyond one team

Why this is ecosystem infrastructure, not a team tool

The prompts are specific to three bots. Everything around them is not.

What is genuinely portable

AssetWhy it transfers to any voice bot
67-pattern taxonomyFailure classes of LLM voice agents — turn structure, tool payloads, TTS, script drift. Nothing KKB-specific.
54 generic checksSilence, barge-in, ASR, no-fabrication, consent, graceful exit, accessibility. Every telephony bot needs all of them.
Agent-to-agent harnessA persona agent calling a bot is a platform capability, not a domain one.
3-tier standardA shared definition of "done" for voice — adoptable as policy on day one.
Sync + divergence modelAny bot in more than one Indian language faces exactly this problem.

Already proven portable once. The taxonomy was applied to Purple Dots — a disability-and-needs bot with a completely different domain — and produced 11 root-caused findings (6 high, 4 medium, 1 to verify) including a swapped latitude / longitude mapping and a hardcoded id contradicting a dynamic search. Different bot, different purpose, same failure classes.

The DPG shape

Voice is how the next hundred million Indians will reach a digital service, and most of those agents will be built by small teams with no QA function. A shared quality-and-testing rail — a reusable failure taxonomy, a checklist standard, and an autonomous test harness — is exactly the kind of horizontal capability a composable public-good ecosystem is supposed to provide.

Why the taxonomy is the moat

It cannot be written from first principles. Every one of the 67 patterns cost a real failure on a real call to a real user. Any team joining the rail inherits all 67 without paying for them — and every bug they hit deepens the catalogue for everyone.

Deliberate scope limits

Today the rail is coupled to one voice platform (its call API and prompt-PATCH endpoint) and its personas are Hindi and Kannada. Both are real portability constraints, and neither is hidden.

18 Adoption

Bringing a new bot onto the rail — the concrete path

Designed so a team can arrive knowing nothing about the tuner and still be useful in the first conversation.

STEP 1

Intake  /onboard

One question at a time: which project, what the bot does, who calls it, every language and which is the master, the prompts, the tools, and each reported issue as its own testable record with an id.

No prompt is touched. Intake gathers and reproduces only.

→
STEP 2

Register  /register-bot

Folder, prompt files, changelog, the path map, deploy targets with hand-copied platform ids, and an entry in the standing-regression fleet.

Outcome: every other skill and script now works on this bot.

→
STEP 3

Audit  /prompt-analyser

Read-only sweep against all 67 patterns and the required-section checklist for its archetype. Returns root-caused symptoms, ranked findings, and missing critical sections.

This is the "strong first version" step. Flags only — never edits.

→
STEP 4

Reproduce  /voice-test

A persona is written for the bot's real audience and the harness calls it. Each reported issue is confirmed — or shown not to reproduce.

Gate: no fix without a transcript.

→
STEP 5

Fix, deploy, stand guard

Snapshot → /update-prompt → mirror → deploy → re-test all three tiers. The bot then appears in tomorrow's digest automatically.

Outcome: it is now covered by the standing net.

Minimum to start

The bot's purpose, its prompt, and one thing that is going wrong. Everything else can be marked TBD. You do not need to fit into KKB, DKB, Maya, Hindi or Kannada — a brand-new project in a language we have never handled is the expected case.

What a new team owes the rail

Platform credentials for their own agents, a decision on which language is master, and acceptance that a fix is not "done" until it is voice-tested per variant. In exchange they inherit 67 patterns, 54 generic checks, and a daily net on day one.

What we owe them

Honest classification. If the transcript shows the inputs were wrong, or the backend 4xx'd, we say "the prompt is fine" and make no edit. A tuner that fixes non-bugs to look busy would destroy the only thing that makes it useful.

A2 Appendix · glossary

The vocabulary, for anyone joining this cold

TermPlain meaning
Conversation promptThe bot's whole script — persona, flow, rules, tool instructions. Up to ~1,600 lines.
Memory promptUpdates what we remember about a caller after each call, so the next call is not blind.
Output promptReads a finished transcript and extracts structured results.
Language-agnosticContent copied verbatim across languages — logic, structure, payloads.
Language-specificContent translated and adapted — only what the bot literally speaks.
Master languageThe language edited first; mirrors are synced from it. Hindi, for all three agents.
VariantOne bot × one language × one direction. The unit that must be tested independently.
Persona agentAn AI agent whose entire prompt is a human character, used to call the bot under test.
TermPlain meaning
Tool callThe bot invoking a real API mid-conversation — look up a caller, apply to a job, post a vacancy.
Modality leakAn outbound bot speaking as if it were inbound — e.g. inviting a callback it cannot receive.
SentinelA placeholder value like "Not Available" or "Any". Never to be spoken aloud.
DriftLanguage twins diverging over time because a change landed in only one of them.
DivergenceAn approved difference between languages. Registered, so sync will not undo it.
Blast radiusEverything a fix could plausibly have broken. Tier 2 tests it.
VERIFY-PENDINGDeployed but not yet proven by a real call. Explicitly not "done".
Fixed for UATDeployed and ready for acceptance testing. Not the same as confirmed.

The three sentences that carry the whole system

1. A rule being present in the prompt does not mean it holds at runtime.
2. No fix without a transcript.
3. Test every variant — never extrapolate.

And the one that keeps it honest

Not every reported bug is a prompt bug. Input errors, backend failures and runtime tool-adherence misses get named and escalated, not prose-patched. Sometimes the correct output is "the prompt is fine, the inputs were wrong" — and saying so is the job.
