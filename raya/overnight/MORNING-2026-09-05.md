## The one you should read first

**A job-seeker could be told there were no jobs while 29 sat in her call arguments.** Measured over
561 calls that were all sent jobs: 11 spoke the missing-job-data line and **5 of those presented
nothing at all** — sent 3, 22, 28, 29 and 29 jobs. Three were **real production callers** on
2026-09-04 (`a7aa424e`, `fef540e9`, `d93b034a`), each with 28-29 jobs in `recommendations`.

Cause: the Input Variables section declared the variable with an alias — *"`${recommendations}` as
job_recommendations"* — and **65 references across six prompts used the alias**, including the
Pre-check that decides whether any jobs were supplied: *"check `job_recommendations`. If it is empty …
trigger No-Match Fallback immediately."* No input has that name, so the condition read as empty on
every call. On a clean call the model reads the populated `${recommendations}` elsewhere and never
consults the pre-check; on a call with poor ASR it takes the first, simplest rule in the section.

Fixed (alias dropped, all 65 references renamed, deployed 16:02 UTC), guarded by a new detector
(`nojobs_integrity.py`), and written up as analyser **D66**. Found by the new overnight sweep on its
**second call** — not by a report.

   tool errors on 2026-09-01→04, six distinct error classes — `ACTION_LIMIT_REACHED` (95),
   `TARGET_ITEM_NOT_FOUND` (20), `MINOR_ACTION_CHANNEL_BLOCKED` (13), `SOURCE_ITEM_NOT_FOUND` (2),
   `INVALID_ITEM_STATE` (2), `PROFILE_LIMIT_REACHED` (1) — **all produced the same generic failure
   line, with not one distinguishing line between them.** Over the same window the model demonstrably
   reads *successful* tool results on every call. The error body is not in what it receives.
   I made two prompt fixes for this, deployed them, tested them, and **reverted both**: `ae2481e6`
   still said "technical issue" on an explicit `ACTION_LIMIT_REACHED`, and `5f0d3671` then said
   "already applied" on an unrelated `USER_NOT_FOUND` — making the branch reachable via a condition
   the model cannot evaluate just moved the lie.

   **It fails in both directions, and that is the argument.** 45 of 60 `ACTION_LIMIT_REACHED` calls
   were told "technical issue" when the application really was in place; and 8 calls in 668 were told
   "your application is already in place" with **neither** of the two kinds of evidence the prompt's

## Found and fixed after the first handover (the sweep kept working)

**Maya read `${college_name}` aloud to the caller.** Harness call `718aa8ab`:
*"नमस्ते। मैं माया, **${college_name}** की ओर से बात कर रही हूँ"*. Three separate rules already forbade
it — *"Never read the raw variable token aloud"*, *"IS A SLOT, NOT WORDS TO SAY"*, and an
empty-case parenthetical — and the bot said it anyway, because the **script** was one quoted sentence
with the slot inside it, introduced as "Use this ONE opening line on every call". The token was the
default and every guard was a caveat. The platform drops empty arguments rather than sending a blank,
so the one case the guards existed for is also the case where the model cannot see anything is
missing.

Fixed the way DKB fixed the identical fault in its Turn 2: print the value back to the model, declare
that **an unsubstituted token counts as empty**, and give **two quoted openers** — one using a
`[college]` slot, one naming no institution — with the institution-free one safe by default. Then I
applied the new heuristic (grep quoted speech for `${`) across the whole fleet: **20 instances in 8
files**, and it corrected something I had told you an hour earlier — I said Maya's inbound prompts
were "already safe" on the strength of one line, and they carried four each. All 15 Maya instances are
now bracket slots. Analyser **D67**, `fix_presence` row added and self-tested.

**Five latent instances I deliberately did NOT touch**, because each sits in a line that has been
observed substituting correctly and the repo rule is the smallest change that fixes the reported
fault:

**And a precise ask that replaces a vague one.** Row 103's escalation used to say "include an
applications list in `get_profile`". Read-only probing of both Signals instances found
**`GET /api/v1/action/fetch` already exists**, works, and validates its query params — but the acting

scoping change, not a build: let the actor read its own actions. With that, the **pre-tool** duplicate
check runs on real data, `apply_job` is never called for a job already applied to, and **both**
